# 单人 + AI 协作的工作流卫生指南

> 背景：项目进入后期，板块多了之后暴露出五个问题——分支管理、半途而废的改动、垃圾分支、需求反复、长对话黑箱。本文是对这五个问题的系统分析和建议，供逐段讨论用。
>
> **现行规则以全局 `CLAUDE.md` 为准，本文是推理过程。** 讨论中定下的纪律后来经过合并精简（例如「未完成工作两个去处」已演进为收工契约里的四分流），细节以规则文件为准，本文不再回头改。

## 0. 总诊断：五个问题里有四个是同一个病

先说结论：**问题 1、2、3、5 不是五种病，是同一种病的四种症状——在制品太多。**

「在制品」（WIP，work in progress）是精益生产借来的词，指已经开工、还没完工的东西。对你来说就是：开了头没落地的改动、跑了一半的对话、留着没删的分支。

它们之间的因果链是这样的：

- 同时开多个对话并行改动 → 超出了你能跟进的数量 → 有的做到一半被遗忘（问题 2）
- 被遗忘的改动躺在分支里 → 变成垃圾分支和死代码（问题 3）
- 并行的改动都没落地 → 互相之间没有同步点 → 跨对话冲突（问题 1）
- 每个对话为了「把事做完」越拖越长 → 你跟不上它在干什么（问题 5）

所以解法不是五套规范，而是一条总原则加几条配套纪律：

> **总原则：瓶颈是你的注意力，不是 AI 的产能。让「同时在飞的事」少到你能全部盯住，让每件事尽快落回 main。**

AI 可以同时开十个代理写代码，但审查、拍板、跟进只有你一个人。产能过剩、审查不足的系统，堆积的就是在制品。这不是你的缺陷，是所有「一人指挥多代理」的工作流的结构性瓶颈——解法在管住进水口，不在提高你的转速。

有一个正交的减负手段：**验收分层**。技术决策全权委托（按推荐执行，不请示），验收拆三层——机器（测试/CI 必须绿）→ AI 互审（独立审查代理在提交前过 diff）→ 用户只验产品行为（界面、交互、文案），不要求读代码。配套约束是**成熟方案优先**（成熟库是被全世界审过的代码，复用即白嫖审查量）和**发布前全库健康检查**（对冲看不见的技术债）。注意：验收分层降低的是「每件事卡在用户处的时长」，不改变「同时在飞的事 ≤ 2-3 件」的在制品上限——验产品行为同样吃注意力带宽。

问题 4（需求反复）是另一种病，单独在第 4 节讲。

## 1. 分支与并行：什么时候拆分支、怎么跨对话并行

### 什么时候拆分支

对这个仓库，答案已经写在 `AGENTS.md` 里了：**默认不拆，直接提交 main。** 这个默认是对的，值得说清楚为什么。

分支（branch）的本质是「一条可以晚点再合并的平行历史」。它的价值是隔离，代价是合并——两条历史分开越久，合并时冲突越多。团队协作里分支是必需品，因为多个人不能都往一条历史上写；但单人项目里，隔离的需求很小，合并的代价照付。这套「默认主干、分支短命」的做法有个名字叫**主干开发**（trunk-based development），是单人和小团队的主流实践。

只有两种情况值得拆分支：

1. **需要 CI 把关的危险改动**——比如动数据库迁移、动发布流程，想让 CI 先跑一遍再合。
2. **可能整个扔掉的实验**——你不确定要不要的探索，做完再决定合不合。

其余一切改动：小步做完，直接进 main。

### 跨对话并行的正确姿势

你观察到的现象很准确：同一对话内的子代理并行没问题，跨对话就难兼容。原因是：**同一对话里有一个「协调者」（主会话）知道全局，跨对话之间没有任何协调者。** 两个对话各自改代码，谁也不知道对方动了什么，等于两个不通气的工人在同一面墙上凿洞。

所以规则是：

- **并行的单位不是「对话」，是「互不相交的文件领域」。** 开第二个对话之前先问自己：这两件事会碰同一批文件吗？会碰就不要并行，排队做。前端某页面 + 后端某命令模块，通常安全；两个都要动 `useSettings` 或同一个页面，必然打架。
- **落地是唯一的同步点。** 跨对话的改动尽快提交进 main（小步提交），后开的对话从最新的 main 出发，就「看见」了先前的改动。改动在工作区里悬着的时间越长，冲突窗口越大。
- **同时在飞的对话 ≤ 2 个。** 不是技术限制，是你的跟进带宽限制。第三件事出现时，写进任务台账（见第 2 节）排队，不开新对话。

### 一个可选的进阶工具：git worktree

`git worktree` 可以把同一个仓库的不同分支同时铺在不同目录里，各干各的、互不覆盖工作区。它解决的是「两个对话同时改文件会互相覆盖」的问题，但**不解决**「合并时逻辑冲突」的问题——两个 worktree 改同一个函数，合并时照样打架。所以它只是把上面「不相交领域」规则的保险丝，不是替代品。仓库里那个 `worktree-agent-*` 分支就是子代理用过的 worktree 残留。知道有这个东西即可，不必现在学。

## 2. 半途而废的改动：给每件事一个「不会被遗忘的家」

问题的机制很简单：**记忆放在对话里，而对话会被关掉。** 对话是易失性存储，你切走注意力的那一刻，里面的未完成事项就开始蒸发。

解法：**把「事情的清单」从对话里挪到一个持久的、唯一的地方。** 对这个项目，现成的答案是 GitHub Issues——仓库已经有 `/feature` 和 `/bug` 两个 skill 直接管理它，不用引入任何新工具。

配套三条纪律：

1. **对话结束规则。** 任何对话结束时，没做完的事只有两个去处：当场收尾提交进 main，或者开一个 issue 写清「做到哪了、下一步是什么、相关文件在哪」。没进这两个去处的，等于主动决定丢弃——而且是显式决定，不是默默蒸发。
2. **新想法规则。** 干活干到一半发现新东西，不转头去追，一句话开个 issue 记下来，回来继续手头的事。想法进了台账就不怕丢，「先记下再回头」比「趁热打铁」少付一次上下文切换加一件在制品的代价。
3. **开工规则。** 每次坐下来干活，先看 issue 列表再决定干什么，而不是凭当下的兴奋度。搁置的东西会重新浮上来，因为它一直在列表上。

「同时进行 ≤ 2-3 件」这条上限，看板方法里叫 **WIP limit**（在制品上限）。它反直觉的地方在于：限制开工数量反而提高完工速度——因为每件事从开工到完工的时间短了，蒸发的窗口也短了。

## 3. 垃圾分支与死代码：定期清扫 + 敢删

### 本仓库现状（2026-08-09，专项清理后）

当天一次专项清理删掉了 **13 条本地空壳分支**（内容全部已在 main，分支只是壳）、**4 条远端旧分支**、**2 个残留工作树**、**1 份零引用的一次性交接稿**，并订正了 3 份内容过期的文档。清理后剩下的非 main 分支只有三个，且每个都有明确身份：

- `codex/mcp-control-bridge-wip` —— **刻意保存的停摆 WIP**，约 9700 行主线没有的 MCP 控制面代码，落后 main 382 个提交。接回需要重做 rebase，做不做是产品决策，不是清理动作。它是「已停摆、非遗忘」——但要维持这个身份，它需要一个 issue 记录去向，否则迟早退化成「遗忘」。
- `codex/mcp-full-surface-audit` —— 工作树已移除，分支保留待用。
- `worktree-agent-acf201d9b80ae212b` —— 正在被另一个运行中的会话检出，不动。

这次清理本身留下了几条值得沉淀的经验：

- **判定「分支是不是空壳」不能信 `git cherry`**——它把同内容不同 patch-id 的提交标成未合入。唯一可信的是内容比对：`git diff --stat origin/main <branch> -- <files>`，diff 为空即空壳。有条分支显示「2 ahead」，实际新增文件与主线逐字节相同。
- **文档里的否定性断言（「还没做」「进行中」）比代码烂得更快。** 三份被订正的文档都是同一种病：写下时为真，功能上线后没人回头改，于是文档反过来指挥人重做已上线的东西。订正手法值得沿用——「只增不改」：原文划删除线加指针，末尾开一章滚动记录「已被后续实现推翻的结论」。
- **分节列修订范围会让名单外的章节静默腐烂。** 一份文档的修订说明按章节列了改写范围，没列到的那一节的「现状表」就停在了改写之前。修订说明要么全文生效，要么明确写出「未复核章节」。

### 原则：git 历史就是你的回收站，所以工作区可以放心清空

很多「留着以防万一」的分支和死代码，留的原因是怕删了找不回来。但 git 的设计恰恰是**一切提交过的东西都永久可找回**——删掉一个已合并的分支，历史一行不少；删掉一段死代码并提交，任何时候 `git log` 都能把它挖出来。所以清扫的心理门槛应该是零。

三条操作规则：

1. **已合并的分支立即删。** `git branch --merged main` 列出的都可以删。GitHub 上有个开关「Automatically delete head branches」，PR 合并后自动删远端分支，建议打开。
2. **超过两周没动的分支，二选一：** 救活（rebase 到最新 main、开 issue、排期）或删掉。不允许第三种状态。这个检查可以挂在每次 `/release` 前做，发布节奏就是清扫节奏。
3. **死代码直接删，不注释掉、不留 `_old` 后缀。** 注释掉的代码是最糟的状态——它不运行（所以会烂掉）、又占着阅读者的注意力（每个看到的人都要想一遍「这还要吗」）。要恢复，找 git 历史。

## 4. 需求反复：降低单次变更的成本，而不是试图冻结想法

这个问题和前三个不同——**它不是病，是早期产品的常态。** 想法在变说明你在学习你自己要什么；「做出来才发现不要」不是浪费，是探索的成本——很多时候不做出来根本不知道不要。试图靠「想清楚再动手」消灭反复，通常只会换来更慢的学习速度。

能优化的不是「变的次数」，是「每次变的成本」。思路是：**把试错尽量往便宜的介质上挪。** 改一句话的成本 < 改一张静态样张 < 改一个实现好的界面，同一个「发现不对」的时刻，发生在越早的介质上越便宜。

你的 `CLAUDE.md` 里其实已经有了最关键的一条：新板块和大改先出静态样张。它的本意就是防这个问题。要让它真正兜住，再补三条：

1. **样张阶段多榨几轮。** 拿到样张别只看一眼「行」，主动挑刺、要变体、把空态/加载态/危险操作都过一遍——在样张上多改十轮，也比在实现上改一轮便宜。
2. **想法过夜。** 新的界面想法先写进 `docs/features/`（一段话即可），睡一晚，第二天还觉得要做再做。今天的兴奋和明天的判断经常不一致，过夜是最便宜的过滤器。
3. **攒批再动。** 界面调整尽量攒成批处理（这也是你记忆里已有的「批量标注截图」工作流），零散的「顺手改一下」最容易引发连锁返工。

另外接受一个事实：某些返工不可消除，它就是产品收敛的代价。目标是让返工发生在样张和文档上，而不是发生在写好测试的实现代码上。

### 「做好」和「做全」是两件事

「讨厌只图今天能跑的偷懒实现」是对的，但它的反面不是「一开始就做到最全面」，而是要拆成两个维度分别执行：

- **质量维度：永不偷懒。** 结构清晰、有测试、用成熟方案、错误处理完整——这些是每一行落地代码的底线，跟功能大小无关。小 ≠ 草率。
- **范围维度：不做超前量。** 只为已经确认的需求写代码，不为「将来可能要」的假想需求提前铺设。为假想需求写的「全面」代码，是另一种技术债：需求真来的时候长得往往和假想不一样，铺好的东西照样重做，还白白增加了此前每一次改动要绕开的体积。行业里这条经验的名字叫 YAGNI（You Aren't Gonna Need It）。

「不如一开始就做好」这个直觉，在**难改的层**成立、在**易改的层**不成立。数据库模式与迁移、同步协议、安全边界、对外接口——这些改起来伤筋动骨，值得一开始多想几步；UI、交互、文案——这些本来就该跟着想法快速变，做「全」等于把最容易变的东西做得最贵。判断标准不是「这功能重不重要」，是「这一层改起来贵不贵」。

真正兼顾长期的做法是：**把「将来好扩展」体现在设计上，而不是把「将来的功能」提前写出来。** 好的结构让下一次需求来时容易加；提前写好的功能只是在赌下一次需求长什么样。本仓库 9700 行停摆的 MCP 控制面分支（issue #14）就是教材：一次性做大做全，方向一搁置，整支代码落后主线数百提交，接回成本逼近重写。

## 5. 长对话黑箱：把「进展的载体」从对话换成 git log

黑箱感的根源：**你把对话记录当成了进度记录。** 对话越长，翻阅成本越高，于是从「我知道它在干什么」滑向「完全不知道」。但其实你手里一直有一份更好的进度记录——git 历史。

三条纪律：

1. **对话按任务切，不按时间切。** 一个对话干一件事，干完、提交、结束。要干下一件，开新对话。长对话不是勋章，是坏味道——它同时意味着任务太大、落地太慢、你已经跟不上了。（对话长了还有个技术性代价：上下文被压缩，AI 自己也开始忘记早先的决定。）
2. **小步提交 + 说人话的提交信息。** 每个提交只做一件事，提交信息写清楚「做了什么、为什么」。这样 `git log` 就是一份你能读的进度报表——看 log 五分钟，胜过翻对话半小时。你最近的提交信息质量已经很好（「首屏那次取数不该防抖——没人打过字」这种就是范本），保持住。
3. **随时要求汇报，这是你的权利。** 感觉跟丢了，直接打断问：「现在的状态是什么？改了哪些文件？还剩什么没做？」AI 汇报状态是零成本的。更好的做法是在任务开始时就约定：每完成一个阶段主动汇报一次，而不是埋头干到底。

还有一条已在你的流程里但值得点名：**非平凡的任务先写实现计划到 `docs/impls/`**。计划文档就是地图——对话再长，你随时可以拿实际进展对照地图，黑箱就变成了「地图上走到哪了」的问题。

## 6. 该补什么课、你个人该练什么

### 系统性补课清单（按优先级）

1. **Git 的心智模型**（最优先）。不是背命令，是理解「提交是快照、分支是指针、历史不可变」这三件事。理解了之后,上面所有「敢删」「小步提交」「历史即回收站」的建议都会从「规则」变成「显然」。资源：《Pro Git》（官方免费，有中文版，git-scm.com/book/zh），读前三章就够。
2. **主干开发**。trunkbaseddevelopment.com，读首页即可，半小时。你会发现本仓库的「直接提交 main」规则就是这套实践。
3. **看板方法的三个概念**：WIP limit（在制品上限）、小批量（small batch）、完成的定义（Definition of Done，一件事什么状态才算「完了」——对你来说就是「提交进了 main 且 CI 绿」）。找一篇看板入门文章即可，一小时。

**不需要学的**（避免绕路）：Git Flow 之类的复杂分支模型（团队协作产物，单人用是负资产）、重型项目管理工具（Jira 等——GitHub Issues 对单人绰绰有余）、企业级 CI/CD 理论。

### GitHub 上有没有现成的技术方案？

有，但都是配角，而且你大多已经有了：

- **GitHub Issues**：任务台账（已有 `/feature`、`/bug` skill 对接）
- **GitHub Projects**：Issues 之上的看板视图，任务多到列表看不过来再启用，现在不急
- **仓库设置里的「Automatically delete head branches」**：合并后自动删远端分支
- **本仓库已有的 CI**：就是你的「完成的定义」的机器裁判

没有任何工具能替你解决「在制品太多」——那是纪律问题，工具只能让纪律的执行成本变低。指望换个工具解决流程病，是常见的弯路。

### 你个人最值钱的三个提升

1. **验产品行为的能力。** 在验收分层（见第 0 节）之下，你不再读代码，但「验产品」要验得狠：空态、加载态、极端输入、危险操作都点到，而不是扫一眼首屏。你是产品正确性的唯一裁判。（读 diff 降级为选修：想学编程时挑感兴趣的提交看——diff 仍是带上下文的、和你切身相关的最好阅读材料——但它不再是提交前的义务。）
2. **把决定写下来的习惯。** 你已经在做（docs/features、docs/impls），把它当成第一等工作而不是额外负担。写下来的决定才能对抗「想法一直在变」——变可以，但要变得有账可查。
3. **单线程纪律。** 发现新东西 → 记 issue → 回到手头的事。这条最难，因为它对抗的是兴奋感。但它是第 0 节总原则在个人行为上的投影：你是系统里唯一的稀缺资源，你的注意力切换一次，全系统付一次代价。
