# 格式规整管线 —— 给验收老师的说明与咨询提示词

这份文件是[验收清单](format-normalization-testing.md)的**外层包装**：清单是给动手的人逐条打勾用的，这份是给第一次接触这件事的人看的——它先解释「在验什么、为什么值得验」，再给一段可以直接复制发给对方的话，最后是我们希望对方给判断（而不只是打勾）的几个问题。

---

## 一、这件事说人话是什么

Lantern 是个电子书阅读器。电子书有很多种格式，其中 **EPUB** 是「活的」——文字是可以被程序读到的结构，所以能划词、能查词、能标注、能让 AI 解释这一段。而 Kindle 那一系的 **MOBI / AZW / AZW3** 在我们的渲染引擎里只能「看」，不能「碰」：打得开，但选不中文字，于是查词、标注、AI 全部失效。

这次做的事情是：**导入 Kindle 格式的书时，在后台悄悄把它转成 EPUB，再让阅读器去读转换后的那份。** 用户什么都不用做，只会看到封面上转一会儿圈，然后这本书就和普通 EPUB 一样好用了。

转换靠的是一个叫 **Calibre** 的免费第三方软件（它自带一个命令行工具 `ebook-convert`）。所以有两条路要分别验：

- **装了 Calibre**：走转换，书变「活」的。
- **没装 Calibre**：完全维持老样子，只能看不能碰——**但绝对不能报错、不能卡死、不能假装在转换**。

第二条路和第一条一样重要。软件最怕的不是少个功能，是「你以为它在做某件事，其实它没有」。

## 二、为什么必须由人来验，代码测试不够

代码层面的自动化测试已经全绿了（466 个后端测试 + 类型检查 + 代码规范检查）。但自动化测试**验不了三件事**：

1. **它跑在没有图形界面的环境里**，看不到封面上那个转圈到底转没转、失败图标出没出来。
2. **它不会真的去调 Calibre**，所以「Calibre 在这台机器上到底能不能被找到」是模拟出来的。
3. **它只有一台机器**，而这套设计里最容易出错的是**两台电脑通过 iCloud 同步**时的行为——转换产物是本地的、不该进 iCloud，另一台电脑要自己重新转一遍。这条只能拿两台真机走一遍。

写这套代码的那次开发没有图形环境，所以**运行时验收一次都没做过**。这就是现在要请人做的事。

## 三、可以直接复制发给对方的一段话

> 想请你帮忙做一次真机验收，顺便给点意见。
>
> 背景：我的电子书阅读器 Lantern 新加了一条「格式转换」管线——导入 Kindle 格式的书（.mobi / .azw3）时，如果电脑上装了 Calibre，就在后台自动把它转成 EPUB，转完之后这本书才能划词、查词、做标注、让 AI 解释。没装 Calibre 的话就维持原样，只能看不能选。
>
> 代码写完了，自动化测试全过，但**运行时和界面从来没有人真的点过一遍**（写代码那次的环境没有图形界面）。所以现在缺的是一次真人验收。
>
> 需要你准备：
> - 一台 macOS，能跑起来这个 app；
> - 装好 **Calibre**（普通拖进「应用程序」即可，不用配置）；
> - 两本 Kindle 格式的书（一本 .azw3、一本 .mobi），外加任意一本普通 EPUB 和一个 PDF 用来做「没被弄坏」的回归对照；
> - 如果方便，**第二台 Mac 并开着 iCloud 同步**——最关键的一组用例在两台机器之间，一台机器验不了。
>
> 详细的逐条清单在这份文档里：`docs/guide/format-normalization-testing.md`，一共 T1–T10 十组用例，每组都写清楚了「怎么操作」和「预期看到什么」。
>
> 两件事请特别注意：
> 1. 文档 §5 列了 5 条**已知限制**（比如删书之后转换产物不清理、装 Calibre 之前导入的老书不会追溯转换）。这些是设计上就这么定的，**遇到了不用当 bug 报**，但如果你觉得其中哪条对真实用户来说不可接受，请直接说。
> 2. 结果请按「通过 / 失败 / 没条件验」三挡记，**「没条件验」不要写成「通过」**。缺条件（比如只有一台 Mac）是完全正常的，写清楚缺什么就行。
>
> 除了打勾，更希望你给几个判断题的意见，见下。

## 四、我们真正想听意见的几个问题

打勾任何人都能打，这几个问题需要经验判断，请对方**用自己的话回答**：

1. **那个「准备中」的转圈，等多久会让你觉得不对劲？** 一本大书可能要转一两分钟。现在界面只有一个转圈，没有进度百分比、没有「预计还要多久」。你会不会以为它卡死了？需不需要加点什么？
2. **转换失败时，用户看到的是一个感叹号，点一下重试。** 但用户不知道失败原因是「没装 Calibre」。要不要直接告诉他「请先安装 Calibre」并给个下载链接？还是说让阅读器提这种要求太啰嗦了？
3. **依赖一个第三方软件（Calibre）这件事本身**，你怎么看？它是免费开源的，但要用户自己去装。有没有更好的取舍——比如干脆不支持 Kindle 格式，或者反过来把转换器打包进来（体积会大很多）？
4. **两台电脑的行为**：同一本书在 A 电脑转好了，同步到 B 电脑上还要再转一遍（因为转换产物是本地的，不进 iCloud，避免占用户的 iCloud 空间）。用户会不会觉得「我不是已经转过了吗」？这个取舍你觉得站得住吗？
5. **有没有哪一条你觉得清单根本没覆盖到？** 写清单的人和写代码的是同一个，所以盲区大概率也是同一个。

## 五、验收结果回来之后

对方给的结果按三挡回填进 [`format-normalization-testing.md`](format-normalization-testing.md)：**通过 / FAIL / BLOCKED**（BLOCKED = 没条件验，不是通过）。全绿之后这份指南和它的验收清单一起移进 `archive/`；有 FAIL 的话，FAIL 项转成 GitHub issue 再归档。
