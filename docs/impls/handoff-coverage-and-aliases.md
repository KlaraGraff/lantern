## 2. 板块一 · 按读者已知词算覆盖率

### 2.1 为什么要做

应用语言学里 Nation 的两条参考线——95% 借助查词能读下来、98% 基本不用查——**主语是读者**：「读者认识的词占文本的 95%」。

Lantern 现在算的不是这个。现有的「词汇难度」区块把书里的词按 Google Books Ngram 词表分 5 档，报第 5 档累计覆盖率。但 band 1–5 加起来就是整张词表，所以那个数测的是**「这本书有多少词在我们的词典里」**，跟读者无关。实测六本书全部落在 94.92%–98.12% 这三个百分点里，而且顺序是乱的：《白鲸》比《物种起源》还「容易」。真正的难度差被挤到了表外（《白鲸》18.50% 未收录，《小王子》5.80%）。换更大的词表只会把这三个点挪到 97–99。

**这块要做的是换主语**，用这位读者自己的已知词集合去数一本书。既有的频段分布不删——它回答「这本书的用词有多罕见」，是另一个问题，两个数并排放。

> 注意措辞：这**不是修 bug**。产品目前根本不计算覆盖率（`src/pages/book-details/difficulty-view.ts` 只有 `hardShare` / `easyShare` / `difficultyVerdict`）。这是新增能力。

### 2.4 缺什么（要新增的）

**(a) 每本书的词形 → 词次表。** 覆盖率是「书的词表 ∩ 读者的已知词集」，现在没有任何地方存着书的词表。

新增 `book_word_counts(book_id, word, tokens)`（表名和字段名你可以改，形状照这个来），在 `compute_and_store()` 里顺手写：那一趟本来就已经把 `count_words()` 的结果算出来了，多一次批量插入而已，不用重新分词。体量很小（《呼啸山庄》12 703 个词形，《白鲸》约 19 000）。跟 `book_difficulty` 共用 `source_sha256`，换文件时一起失效。

**不要**每次算覆盖率都重新扫全书——样张 05 态的进度条是给「扫全书词表 × 词汇画像求交集」留的，不是给重新分词留的。

**(b) 覆盖率结果表。** 一本书一行：覆盖率、各档词次、算于什么时候、用的哪份画像。样张 05b 要求重算时旧值继续显示，所以旧值必须落库，不能只在内存里。

**(c) 已知词集的定义。** 样张 01 的「这本书的词次构成」四行就是分类口径：

| 样张里的行 | 数据来源 | 是否算「认识」 |
|---|---|---|
| 已掌握 | `vocab_words.mastery IN ('familiar','mastered')` | 是 |
| 眼熟 | 见下（D2） | 是（可在设置里关掉） |
| 人名地名 | 见下 (d) | 是 |
| 还没掌握 | 其余 | 否 |

**「眼熟」的口径已定（D2）：** `mastery_progress.credit >= FAMILIAR_CREDIT / 2`（`FAMILIAR_CREDIT = 4.0`，`mastery/mod.rs:124`，即已经走完通往「已掌握」一半的路）**且**该词在 `reading_word_exposures` 里查词次数为 0 **且**不在已掌握集合里（去重，别把同一个词数两遍）。

这么定是因为 `mastery_progress`（039）本来就是「还没到档位的半成品信用值」——那正是「眼熟」的意思，直接复用现成刻度，不新造常量。查过词的排除掉：查过就是不认识的直接证据。取「一半」是唯一不需要额外论证的分点，而且这个选择的误差被区间吸收了——门槛调松只影响上界，下界纹丝不动。

设置里那一行「覆盖率把『眼熟』算作认识」控制的就是第二行是否计入。样张 01 同时给出了两个数（96.4% 含眼熟 / 90.6% 只算已掌握），**两个都要能算出来**，(e) 的区间也要用到它们。

**(d) 人名地名的判定（已定）。** 样张把它单列一档并计入「认识」，理由写在界面上：一个反复出现的名字，第一次之后就不再花力气。口径：不在词频表里（即落进 `band_unlisted`）**且**在原文中以大写形式出现；再并上 `book_person_aliases` 里这本书的全部 canonical 和 alias 文本。展开态（06）的未掌握词清单里**不能**出现人名地名。

会有误判——某个真的生僻词碰巧在句首大写。可以接受，不要为它加机制：它只会让覆盖率略偏高一点点，而人名当生词列出来对读者的干扰要大得多。

**(e) 「样本不足」的区间怎么算（D1，已定）。**

样张 04 给的是 93.1%–97.9% 这样一段区间，会随着读的量自己收窄。规则定为：

> **两个边界永远都算。**
> - 上界 = 已掌握 + 眼熟 + 人名地名，都算作认识。
> - 下界 = 只算已掌握 + 人名地名。
>
> **给点还是给区间，看两道门槛，两道都过才给点：**
> 1. 读过的书 ≥ `MIN_BASELINE_BOOKS`（= 2，`difficulty-view.ts:78`，直接复用这个常量，不要新造）。
> 2. 区间宽度 ≤ 1 个百分点。
>
> 两道都过 → 显示一个点，取上界（即设置里「把眼熟算作认识」开着时的那个值；关掉时取下界）。
> 任何一道没过 → 显示区间，走样张 04 的版式。区间横跨 95% 时按样张明说「现在分不出来」。

理由，值得知道，因为它决定了你别去加统计机器：

这个区间**恰好就是不确定性本身**。系统不知道该对「眼熟」有多宽容——它可能全都真认识，也可能一个都不认识，两个极端就是上下界。读得越多，眼熟里被确认成已掌握的越多，区间自然收窄。所以它单调、可解释、零额外计算，而且**不需要任何凭空定的阈值**：宽度门槛不是在猜样本够不够，它是在直接测量「这个不确定性还大不大」。

「≥2 本书」那道门槛是防一种反常情况：读得极少的人可能碰巧没几个眼熟词，区间假性地窄。它复用现成常量，不引入新数字。

**不要**引入「已知词形 ≥ N」这类下限——那个 N 没有来源，会变成第二个 `MIN_MEDIAN_PACE_SAMPLE`（仓库里唯一一个没有依据的常量，见 `commands/reading_behavior.rs`）。宽度门槛已经把它的活干了。

**(f) 危险操作的爆炸半径。** 样张 09 已经把边界写死了，实现必须严格对上：

- 清除：`mastery_source = 'auto'` 的档位、`reading_word_exposures` 全部、`mastery_progress` 全部、已算好的覆盖率。
- **不动**：用户手改过的档位（`mastery_source = 'manual'`）、生词本与 FSRS 复习状态（`fsrs_stability`、`fsrs_difficulty`、`next_review_at`、`review_interval_days`、`last_reviewed_at`、`last_review_rating`、`review_count`）、查词记录、标注、笔记、每本书自己的词频分布、`reading_screen_dwells`。
- `src-tauri/migrations/064_reset_polluted_exposures.sql` 就是这套范围的一次性版本，**直接照抄它的 SQL**，别自己重新推一遍。

## 3. 板块二 · 人物别名表可见与可改

### 3.1 为什么要做

每本书导入后会调一次 LLM 建「别名 → 书里的写法」表，问答靠它把「达西怎么想」接到 `Mr. Darcy` 上。实测这张表约八成对（25 条里 5 条错）。最伤的一类是**把两个人合并成一个**：`Vesely-Frankl` 被整个判给 Alexander，而书里还有一个 Franz Vesely-Frankl，于是问 Franz 的问题被答成 Alexander。读者看不出来，只会觉得「AI 乱答」。

建表侧的三处校验已经修完并提交（`e7fb678`）：逐条丢弃零命中别名、拒绝常见词单词 key、漏抓的人扩成第二 canonical 走已有的歧义路径。**这一块是界面侧**——让读者看得见、改得动。

### 3.2 这不是新增，是改造现有那一节

**关键前提，别跳过：这张表已经有界面了。**

- `src/components/PersonAliasesSection.tsx`（491 行）—— 增、删、重建、清空、错误态、描述别名都已实现并接了后端。
- `src/components/person-aliases.ts` —— 纯逻辑层（`personAliasRows()`、`aliasTableCounts()`），无 React 无 Tauri，可单测。
- 挂载点：`src/components/IndexManagerModal.tsx`（约 :420）。
- 后端命令全在 `src-tauri/src/commands/ai/person_aliases.rs`：`list_person_aliases` / `build_person_aliases` / `add_person_alias` / `teach_description_alias` / `delete_person_alias` / `clear_person_aliases`。
- 存储与解析逻辑在 `src-tauri/src/ai/grounding/aliases.rs`。

**位置不变**：还是 `IndexManagerModal` → 「人物别名」一节。它现有三个入口（书库右键菜单 `BookList` / `BookGrid`、阅读器内 AI 面板的索引按钮 `AiPanel`），语境都对。

### 3.3 今天缺的三件事

**(1) 歧义完全不可见。** 表按「书里的写法」分组，一个别名指向两个人就变成两行里两个长得一样的普通标签，中间没有任何连线。后端其实知道——`resolve()` 遇到这种会降到 `Medium`，答复上方会出现一行提示——表里却什么都不说。

**(2) 出现次数取到了却没显示。** `AliasEntryView.mentions`（`aliases.rs:63`）一直在返回，界面从来没画出来。它是判断「这条是不是模型编的」最直接的证据：模型编的名字次数会低得离谱；`Young` 这种被当人名的常见词次数会高得离谱（`count_mentions` 用的是大小写不敏感的 `LIKE '%Young%'`，会命中每一个 young man）。按次数排序之后两头的异常都浮到眼皮底下。

**(3) 长表没有收纳。** 所有人平铺。一本长篇几十上百人，真正需要看的那三条被淹掉。

另有两处今天**没有确认就执行**：删一条别名点 × 立刻删；重建点了立刻调模型花钱。只有「全部清空」有确认。

### 3.4 状态清单

| # | 状态 | 要点 |
|---|---|---|
| 1 | 正常态（长表默认收起） | 三段式：需要确认的（永远展开，通常 0–2 条）→ 出现次数前 8 的人 → 其余折成一行。**折叠条上要写清被折走的都是多少次以下的小角色**，只说「还有 31 人」读者还是得点开 |
| 2 | 歧义条目 | 「桥卡片」放在表上方，一张卡装下两个候选；表里的标签（`⑂ 2 人`）只是它的入口 |

### 3.5 每条的实现要点

**歧义（状态 2）**

- **不需要新后端命令。** 歧义完全可以从 `list_person_aliases` 已经返回的 `AliasGroupView[]` 推出来：同一个 alias 文本出现在两个 canonical 下面，就是歧义。放进 `person-aliases.ts` 做成纯函数，好写测试。
- **文案必须说准。** `resolve()` 把**两个规范名都追加进检索词**（`expanded_query`），并不只查一个；`default_canonical` 只决定答复上方那行提示写谁的名字。所以写「两个名字都会拿去检索，不会漏掉谁」，**不要**写「系统会猜一个」——后者会让读者以为另一个人被丢掉了，从而去删掉一条本来正确的别名。
- **视觉：黄色描边，不是填色。** 红色在这套界面里只归破坏性操作；歧义不是错误（书里真有三个 Frankl）。填色的黄已经被描述别名（`≈`）占了。
- 桥卡片上的「改成只指 X」在后端就是删掉另一条 `(alias, canonical)` 行，现有 `delete_person_alias` 够用。它是破坏性的——**走一遍状态 7 的就地确认，同一套文案**（D8，已定）。

**行高（状态 1）**

- **不要用 73px。** 73px 是设置弹窗的行规范（`GeneralSettings.tsx`），这是索引弹窗里的一张数据表，现有实现用的是紧凑行（`py-2`），样张跟现有实现走。一行 73px 的话八个人就占满整屏。

**添加别名（状态 6）**

- 路径二的「指向谁」现在是一个自由输入框（占位符「书里的写法，例如 Mr. Darcy」）。手打一个书里不存在的写法，`add_person_alias` 会把 `mentions` 算成 0 然后**照存不误**，界面上看不出任何异常，读者以为教会了，其实这条永远命不中。
- 改成边打边找。**候选先只查 `book_person_aliases` 里已有的 canonical**（零成本，现有数据够），再加一条「就用我打的」兜底。
- 「书里有但表里没有的人也能选出来」需要一个按前缀扫 `book_chunks` 的新命令——**本期不做**（D10）。

**删除确认（状态 7）**

- 就地展开，不弹窗。删别名是高频、低后果的操作（一本书可能 78 条，读者会连删五条），每条弹一个居中模态会把清理这张表变成折磨。
- **两种来源两种话**：自动认的那条，真正的后果是「重建时它可能回来」；你教过的那条，后果是「删了就没了，重建也拿不回来」。同一句通用文案说不清这两件事。
- 都只陈述后果，不加「确定吗」「此操作不可撤销」这类吓人的话。

**重建确认（状态 8）**

- **一处必须纠正的事实：重建并不覆盖读者手动改过的条目。** `clear_auto_aliases`（`aliases.rs:272`）只删 `source = 'auto'` 的行，`run_build_pass` 写回时也不动已经是 `'user'` 的行。所以确认文案**不能**说「会覆盖你改的」——那是假的，说了会让读者不敢按这个本来安全的按钮。真正会丢的是**你删掉过的自动条目可能回来**（删除没有被记下来）。
- 「要花一次模型调用的钱」**不写具体金额**——各家模型价格差太多，写死会骗人。写清楚是一次、一本书、最多重试三次，读者拿自己的价目表就能估。
- 重建用中性框，清空用红框。重建可重复、可再来一次；清空是唯一会毁掉不可重建数据（手教的行）的操作。两个都涂红，红色就不再意味着什么了。

**新入口：从答复里进来（D9，本期要做）**

歧义真正被发现的时刻，是读者看到答复上方那行「「Frankl」按「Viktor E. Frankl」找的」并觉得不对的那一秒。那行（`src/components/AliasDisclosure.tsx`）现在只能「换成 Franz」一次性改这一轮；再给一个「管理这本书的别名」的去处，打开 `IndexManagerModal` 的人物别名一节，并滚动/高亮到对应条目。落不到具体条目就退化成只打开那一节，不要为此卡住。

**为什么按书存，不做成全局表**（界面上要说这句）：同一个称呼在不同书里可能是不同的人。一张全局表会把从一本书学到的东西泼到另一本书上，越用越糟。

## 4. 交付顺序与接续

两块互不依赖。**先做别名表**：它没有新数据模型、没有新后端命令、爆炸半径小，很快能看到东西；覆盖率要新表、新计算、八个状态，是个更大的工程。有两个人的话可以并行，没有依赖。

每块内部的顺序：

1. 纯逻辑层 + 单测（`person-aliases.ts` / 覆盖率的计算函数）
2. 后端命令 + 单测（只有覆盖率需要）
3. 前端状态逐个接上，空态和失败态**先做**，别最后补
4. 危险操作的确认与爆炸半径**最后做但必须做**，且要真的验一遍删了什么、留了什么

**这活比一次连续工作能装下的量大，所以按可中断的方式做：**

- **每完成一个上面的小步就提交一次**，直接进 `main`，提交信息说清这一步做完了什么。不要攒大提交——中断时未提交的工作就是全丢。
- 提交前保证 `cargo test` / `npm test` 是绿的。半成品也要能编译、能过测试；宁可少接一个状态，不要留一个跑不起来的中间态在 `main` 上。
- **中断后重新开工，先做这三件事**：读本文件、`git log --oneline -15` 看上次做到哪、`git diff` 看有没有没提交完的活。本文件 + 两份样张 + 提交历史合起来就是全部上下文，不需要问任何人。
- 全部做完再一次性汇报：做了什么、§0.5 之外你另外定了哪几件事、哪里跟样张不一样以及为什么、验收命令的实际输出。

## 5. 已知的坑

- **测试跑完要看退出码。** `cargo test ... 2>&1 | tail -15` 的退出码是 `tail` 的，永远是 0。重定向到文件再看。
- **`cargo` 可能不在 PATH 里**，需要 `export PATH="$HOME/.cargo/bin:$PATH"`。
- **不要对整个文件跑 `rustfmt`。** CI 不检查格式（`.github/workflows/ci.yaml` 里没有 fmt 步骤），全文件格式化会在 diff 里塞几十行无关重排，审查时得一条条挑出来。只格式化你自己写的部分。
- **无头截图会重挂 React 树。** 用 CDP 走查界面时用高视口 + `captureBeyondViewport: false`；如果状态莫名回到初始值，先怀疑截图而不是代码。
- **`Db::open_readonly` / `open_readwrite` 把读写两个连接别名成同一把锁**（`db.rs:295`、`:327`）。持有 `db.conn.lock()` 的时候再调 `db.reader()` 会自己锁死自己。正常 app 路径（`Db::new`）是两个独立连接，安全；只有 `lantern mcp` 子进程用那两个构造器。覆盖率如果要在一个事务里同时读词频表和书表，注意这一点。
