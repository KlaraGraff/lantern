# Lantern 推广方案

面向图文平台（小红书为主）的冷启动方案。目标不是「涨粉」，是让**愿意配置 API Key、能跨过 Gatekeeper 提示的那批人**先用起来并留下反馈。

---

## 零 · 先承认三个会直接卡住转化的事实

推广之前必须先处理这三件事，否则流量来了也留不住。

### 1. 需要自己配 API Key —— 这是最大的一道门槛

Lantern 不带 AI 服务，用户得自己去 OpenAI / Anthropic / 硅基流动 / DeepSeek 或本地 Ollama 拿一个 Key 填进去。对技术人群这是加分项（省钱、可控、数据不过第三方），**对普通英语学习者这是劝退项**——大部分学生不知道 API Key 是什么。

这直接决定了推广顺序：**先打技术 / AI 工具人群，再打英语学习人群**。前者能自己跨过去，还会帮你写教程；等有了现成的配置教程和真实用户案例，再去打后者，转化率会高得多。

**要做的事**：写一篇《3 分钟配好 AI 服务》图文，用最便宜的国内可用方案演示（比如 DeepSeek，几块钱能用很久），从注册到填进 Lantern 全程截图。这篇本身就是一条内容，也是所有其他内容的落地承接。

### 2. ~~macOS 会弹「无法验证开发者」~~ 已解决，但别自己把它讲回来

**这一条已经不成立了。** 仓库配了 Apple Developer ID 证书，正式版（不带连字符的 tag）走真实签名并提交公证，用户双击就能装——细节见 [macOS 发布与签名](../guide/macos-distribution.md)。

留着这一节是因为它现在的用法反过来了：

- **推广文案里不要出现 `xattr` 那条命令**，评论区置顶也不要。写了等于告诉每一个潜在用户「这个软件系统不认」，而事实是它认。这是纯粹的自伤。
- **也不要主动写「已签名并公证」当卖点**。用户不关心，写出来反而让人以为这里本来有问题。
- Release 说明里那句签名状态由 CI 的 `release-notes` job 按实际发生的情况自动写，**不要手改**。预发布 tag（带连字符）确实只有 ad-hoc 签名，但那种包不会推给任何人，也不该被拿去推广。
- **推广前先确认要推的那个版本是正式 tag、公证过了、并且从 GitHub 附件重新下载验证过能双击打开**。用本机构建的产物做判断不算数。

### 3. 只支持 Apple Silicon Mac 和 Windows 11

Intel Mac、iPad、手机都用不了。文案里主动写明，别让人下载完才发现——被骗一次的用户不会来第二次。**尤其不要在内容里承诺 iOS**，它现在只跑通了模拟器。

### 顺手要改的免费流量入口

- ✅ **仓库描述已改**，并已随 README 重新定位再改过一次——现在讲的是上下文和引用，不再只讲分级解释。**用英文而不是中文**——描述带来的流量主要来自 GitHub 的 topic 页面和站内搜索，那是英文场；中文平台的流量是直接点链接到 README 的，看不到这一行。
- ✅ **Topics 已加**（16 个，含 `rag`）。GitHub 的 topic 页面是真有人逛的，找 grounding / 引用方案的人会从 `rag` 进来。
- ✅ **Homepage 已填** Releases 页。

| 封面模板 | 1242×1660（3:4） | 每条图文的第一张 | 待做 |
| 内页模板 | 1242×1660 | 图文第 2–8 张 | 待做 |
| 3 段录屏 | 15–30 秒，转 GIF | 平台视频位 + README | 待做 |
| 一句话定位 | 30 字内 | 所有平台简介 | ✅ 已定 |
| 100 字介绍 | —— | 正文开头通用段 | ✅ 见 README |

**一句话定位**（统一口径，所有地方用同一句）：

> 把 AI 放进书里，而不是把书搬进聊天窗口——它知道你的英语水平、读到哪、这段前后写了什么，答的每一句都能点回原文。

**为什么不是「解释跟着你的英语水平走」了。** 那句只说了 AI 拿到的众多上下文里的一条，把整个产品缩成了一个查词工具。真正的差异点是**上下文**：水平、进度、书目章节、选中处前后、整本书的检索，全都随每一次请求过去，而且答案能点回原文。分级解释是这件事的一个结果，不是这件事本身。

面向学习人群写文案时，仍然可以从「解释比原文还难」这个具体痛点切入——那是最好懂的入口——但落点要收在上下文上，别停在分级。

## 二 · 图片具体怎么做

你问的重点。分三类，做法完全不同。

### A. 界面截图 —— 脚本拍，不手拍，更不要生成

```bash
node scripts/shoot-readme.mjs
```

这个脚本起真实的 React 前端和真实的 foliate-js（只有 Tauri 那一侧是 mock），把界面驱动到指定状态再截图，输出到 `assets/screenshots/`。**应用渲染不出来的效果，图上就不会有**——这正是要的：宣传图和产品之间不留缝。

三条纪律：

- **不要用图像模型生成界面。** 生成的按钮和文字一眼假，砸的是产品可信度。
- **不要手动 `⌘⇧4` 补拍。** 手拍的图带着当时的本机数据和窗口尺寸，换一版就对不上，而且没法重拍。脚本每次拍出来一样。
- **图里的书必须是公版书。** README 是公开的。样张书架用的是 Standard Ebooks 的 12 本（`harness/promo/library.ts`），全部美国公有领域，封面用的也是公有领域画作。

镜头清单在 `scripts/shoot-readme.mjs` 的 `SHOTS` 表里，`name` 必须和 README 里 `![](…)` 引的文件名一致。单拍某几张：`node scripts/shoot-readme.mjs hero coverage`；试拍别脏仓库：`--out=/tmp/shots`。

### B. 封面图 —— 决定点击率的那一张

图文内容 80% 的成败在封面。结构就三层：

```
┌─────────────────────────┐
│  大字标题（14–18 字）      │  ← 占上方 1/3，字号要大到手机上一眼看清
│  一行小字副标题            │
│                         │
│  ┌───────────────────┐  │
│  │   产品截图（裁切）    │  │  ← 占中下部，只露最有信息量的局部
│  └───────────────────┘  │
└─────────────────────────┘
```

规格与做法：

- **尺寸 1242×1660（3:4）**，这是小红书的首图比例，竖版在信息流里占面积最大。
- **标题必须是痛点或结果，不是产品名。**「用 AI 查词，结果解释比原文还难」比「Lantern 上线了」的点击率差一个量级。
- **截图要裁切，不要放整个窗口。** 整窗缩到手机屏幕上什么都看不清。只露那张查词卡，或只露提示词输入框。
- **背景用产品自己的暖色纸底色**，全套内容配色统一，刷到第三条时别人能认出是你。
- 工具：**Figma**（免费，做一个模板然后换字换图）或**稿定设计**（有现成中文模板，更快）。

### C. 对比图和说明图 —— 你最该多做的一类

「AI 拿到了上下文」是个抽象说法，对比图是把它落地成一眼能看懂的东西的最好办法——这类图的信息密度和转发率也最高：

1. **分级解释对比**：同一个词，左边 A2 的解释、右边 C1 的解释，中间一条分隔线，上方标注等级。一张图说清「它知道你的水平」。
2. **「别的工具 vs Lantern」**：左边一段谁都看不懂的母语级英文解释（可以是真的，从别的工具截）、右边 Lantern 的分级解释。**注意：别点名踩其他产品**，写「常见的 AI 查词」就行，点名会招黑。
3. **自定义模块的前后**：左边默认卡片、右边加了自定义模块之后的卡片。模块要挑一个内置做不到的——样张用的是「现在还这么说吗」（这词今天还常用吗、换成什么说法）；「长难句拆解」不行，内置的「全句脉络」已经是那件事了。
4. **引用跳转的左右对照**：左边 AI 给的生词清单（每条带角标），右边点击后跳到的原文，被引用那一句高亮着，中间一个箭头。这张图不需要一个字的解释——箭头本身就是全部信息。
5. **「聊天窗口 vs Lantern」的上下文对照**：左边一个通用聊天窗口，只有你粘进去的那几行字；右边 Lantern 的侧栏（`context.png`），带着阅读进度提示、回答范围和原文来源。这张图讲的是新定位本身，但**它需要一句标题才立得住**，不像引用跳转那样自明——适合放在图文的第二张，不适合当封面。

> `context.png` 目前在选题表里没有对应的一条。「AI 默认不拿你还没读到的地方回答你」值得单独做一条，切入点是**「我给我的 AI 阅读器加了一个不剧透的开关」**这类具体说法——但要避开「防剧透」当主标题，那个词会把这件事说小。

### D. 录屏 GIF —— 四段就够

| 内容 | 时长 | 要点 |
| --- | --- | --- |
| 双击一个词 → 卡片弹出 → 内容流式生成 | 15 秒 | 展示速度和流畅度，这是最有说服力的一段 |
| **点一下回答里的角标 → 书翻到那一页 → 那一句闪一下** | **5 秒** | **全套素材里最好的一段**。它是一个动作、一个结果，不需要任何解说文字，而且静态图讲不清楚 |
| 写一个自定义模块 → 保存 → 卡片上出现 | 30 秒 | 展示「可改造」，要加速播放 |
| 选中一段 → 朗读 → 逐句高亮跟随 | 15 秒 | 有声音的功能必须用动图讲 |

工具：**Kap**（免费，macOS，直接导出 GIF）或 **Gifski**（压缩质量最好）。GIF 控制在 5 MB 以内，README 里也能放。

### E. AI 生成图的边界

只用在这两处：**内容封面的背景纹理**（纸张质感、书页光影、暖色渐变），和**抽象概念配图**（比如画「读书时被打断」的意象）。**绝不用来画产品界面**。

| 12 | 「和 AI 聊过的东西，不会丢在聊天软件里」 | chats.png 对话归档 | 技术 / AI 工具 |

**第 2 条和第 6 条是同一个功能的两种说法，这一点值得单独说。** 引用跳转对两批人的价值完全不同，所以文案也必须完全不同：

- **对技术人群**，借 NotebookLM 这个名字最省力——他们知道 grounding 是什么，也知道它难做。差异点一句话说完：*NotebookLM 的引用只能跳到侧栏里的一段文本，而 Lantern 本身就是阅读器，引用跳回的是书里真正的那一句。*
- **对学习人群**，NotebookLM 这个词是无效信息，得换成场景：*读之前先让它把这一章的生词列出来，得到一份长清单，每一条都能点回原文那一句。* 不需要任何前置知识，而且是一个他们真的会做的动作。

这条选题的另一个优势是**它天生适合做动图**：点角标 → 书翻页 → 那一句闪一下。三秒钟，不用配文字。**在信息流里，能用动作说清的东西永远比用文字说清的传得远。**

**第 12 条打的是一个别人没在说的痛点。** 所有人都在讲 AI 能回答什么，没人讲**那些回答后来去哪了**——在聊天软件里，它们混在报销流程和菜谱中间，三天后翻不出来，翻出来也想不起当时读到哪。Lantern 里对话按书归档，点一下就带着你回到书里那个位置继续。这条内容不需要解释任何技术，而且**用过 ChatGPT 读过东西的人一秒就懂**。

这条不必只讲对话。生词和笔记是同一个机制：每一条都记着自己是从哪一句里来的，生词卡上直接带着那段原文和它在那一句里的意思，点「在阅读器中打开」同样落回原句。面向学习者的那一版可以用 `vocab.png` 代替 `chats.png` 开场——「背单词 App 里的词是从列表里冒出来的，Lantern 里的词是从某一句里摘下来的」，同一个论点，换一批人听得懂的说法。

**第 8 条是最容易被低估的一条。** 词形标记是个「细节型」功能——它不宏大，但一说就懂，而且能一眼看出「作者是真的自己在用这软件」。这类内容在小红书的完播和收藏都很好，因为它给的是一个具体的、可验证的小惊喜，而不是一句宏观的产品主张。**这种「想得真细」的内容比功能罗列有效得多**，也最难被别的产品抄走叙事。

**但这类选题有一条筛选标准：不解释实现也能懂。** 词形标记过关——「查了 run，全书的 ran 和 running 一起被标出来」，一句话说完，不需要背景知识。不过关的例子：标记的加粗默认关闭（要先讲分页重排才说得通）、选色时的撞色警告（要先讲系统标记有哪几种）。这些是工程品味，写在 README 里技术读者会欣赏，但放到图文平台就得先铺两句背景——**凡是需要铺垫的，在信息流里都已经输了**。

同一类里还能用的：

- **朗读会自己挑音源**——查一个单词给你词典里的真人录音，读一整段换成神经语音。不用解释任何东西，一听就懂。
- **生词的三档颜色是一条渐变**——新词是暖橙，学习中转青，已掌握变成灰色虚线，越熟越不打扰你。这个是纯视觉的，一张图就说完了。

**第 1 条值得单独说：做软件的过程比软件本身更有传播力。** 你提到很多人在平台上分享自己 Web Coding 的项目——那类内容起量靠的是「一个人 + AI 做出了完整产品」这个叙事，不是产品功能。真实的开发数据（多少个 commit、做了多久、踩了什么坑、AI 帮了什么没帮上什么）比任何功能介绍都更容易被转发。这条建议**第一条就发**，用它把人带到 GitHub。

## 四 · 平台选择和节奏

### 平台优先级

| 平台 | 优先级 | 理由 |
| --- | --- | --- |
| **小红书** | 高 | 图文形态最成熟，英语学习和效率工具两个池子都在这 |
| **即刻 / X** | 高 | 技术和 AI 工具人群密度最高，冷启动最快 |
| **V2EX / Hacker News** | 中 | 一次性曝光，适合发「开源了」那条 |
| **B站** | 中 | 需要视频，成本高，但长尾流量好 |
| **抖音 / TikTok** | 低（初期） | 视频优先，图文权重低；且这个产品需要「看得懂界面」，短视频节奏不适合 |
| **Product Hunt** | 后期 | 等英文 README 和截图齐了再发，一次机会别浪费 |

TikTok 值得说明一下：你看到的 Web Coding 分享确实在那，但那类内容的核心是**「做的过程」而不是「做出的东西」**。如果你要做 TikTok/抖音，选题 1 那个方向才成立，功能介绍在那个平台是发不动的。

### 四周节奏

- **第 0 周**：拍截图、做封面模板、写配置教程、改 GitHub 描述和 Topics。**一条内容都别发。**
- **第 1 周**：发选题 1、2、3、4 到即刻 / X / V2EX。收第一批反馈和 bug，快速修。
- **第 2–3 周**：小红书起号，发选题 5、6、7、9。每周 2–3 条，同一套配色。
- **第 4 周**：看数据决定加码方向。如果 5/6 起量就深挖学习向；如果 1/2 起量就深挖 vibe coding 向。
- **之后**：Product Hunt + B站视频。

## 五 · 别做的事

- **别投流。** 产品还没验证留存，付费流量买来的都是一次性下载。
- **别一次全平台铺开。** 每个平台的内容形态不一样，同一套东西到处发，哪个都做不好。
- **别在文案里承诺 iOS 版。** 说了就得兑现，现在兑现不了。
- **别用在版书的封面截图。** 推广图会被大量转发，用公版书。
- **别点名踩其他阅读器。** 对比可以，点名会招来对方用户的反扑。
- **别把「用 AI 写的」当卖点讲给学习人群。** 对技术人群这是加分，对普通用户这会让他们担心质量。同一件事，对不同人群要换说法。
