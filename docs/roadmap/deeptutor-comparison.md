# DeepTutor 拆解：Lantern 能学什么

> 调研日期 2026-08-09。对象：[HKUDS/DeepTutor](https://github.com/HKUDS/DeepTutor) v1.5.11，
> 33.4k stars，Apache 2.0，港大 HKUDS 组主导。
> 一手材料：仓库 README / README_CN、论文 *DeepTutor: Towards Agentic Personalized Tutoring*
> (arXiv 2604.26962)。
>
> 这不是「要不要抄」的清单。DeepTutor 是通用学习工作台（Python/FastAPI + Next.js，服务端
> 形态，联网、云索引、多用户可选）；Lantern 是单机英语精读器（Tauri + SQLite，本地优先、
> iCloud 同步、零后端）。形态差得远，**能搬的是结构性决定，不是功能**。
> 每节都分四段：它怎么做 / Lantern 现状 / 学什么 / 明确不学什么。

---

## 一、记忆三层（L1/L2/L3）与 Memory Graph

### 它怎么做

DeepTutor 的记忆是**文件系统上的三层金字塔**，刻意不用隐藏的向量库：

| 层 | 存储 | 内容 |
|---|---|---|
| L1 | `trace/<surface>/<date>.jsonl`，append-only | 原始事件流，按「面」分文件 |
| L2 | `L2/<surface>.md` | 每个面的整理后事实，**引用 L1 的事件** |
| L3 | `L3/{profile,recent,scope,preferences}.md` | 跨面综合画像，**引用 L2** |

「面」（surface）是七个能力入口：chat、notebook、quiz、kb、book、tutorbot、cowriter。

三条设计决定值得记：

1. **单向引用链是硬约束。** L3 引 L2，L2 引 L1。官方说法：「你的画像里没有任何一条追不回
   到确切原始事件」。这不是可选的可解释性装饰，是数据结构本身的形状。
2. **Memory Graph 是一等公民的界面。** 把金字塔画出来：L3 在中心、L2 中环、L1 外圈，点任何
   一条综合结论都能一路下钻到原始事件。记忆是**可看、可编辑**的，不是黑箱。
3. **整理是有预算的后台作业。** 设置里能调 integrator 的更新预算、审计频率、去重策略——
   也就是说 L1→L2→L3 的提升是**异步的、花钱的、可配额的**，不是每次交互实时重算。

论文侧的 Trace Forest 比 README 更细：画像更新由三个并行的 memory agent 主动查
TraceToolkit（SearchTrace / ListTraces / ReadNodes）产出三种视图——会话摘要 𝒟ₛ、
**有证据支撑的反复困惑与错题模式清单 𝒟w**、教学自反思 𝒟r。检索时按层分配 token 预算，
兼顾宽上下文和细粒度先例。

论文自己承认没说清的两件事：**层间提升的自动触发条件**，和**冲突/过期的处理**（只在相关
工作里提了 HiMem 的 conflict-aware reconsolidation，自己没做）。

### Lantern 现状

**我们已经独立长出了同一个金字塔，只是没人这么叫它，也没有一个地方能看见它。**

- **L1（原始证据，append-only，全部设备本地）**
  - `reading_word_exposures`（037）——每个词在每章被看见多少次、其中多少次是在「同屏有别的词被查了」的情况下看见的
  - `reading_screen_dwells`（037）——每屏停留时长、操作数、查词数、词数
  - `lookup_records`（014/034）——查词历史
  - `mastery_events`（038）——每次掌握度变化，带 `reason` 机器码 + `detail` JSON（算出结论的那几个数字）
  - `profile_events`（056）——读者对画像卡的每次修正：delete / move / undo / rewrite / effect
  - `level_observation_dismissals`（042）——每次等级提示的处置
- **L2（每个面的结论，带证据）**
  - `vocab_words.mastery` + `mastery_source` + `mastery_reason`——结论、是谁定的、以及**反规范化保存的一句理由**
  - `profile_cards`（056）——七个固定维度各一张卡，`conclusion` 进 prompt、`evidence` **永不进 prompt**
- **L3（进 prompt 的综合）**
  - `profile.user_text`（读者自己写的自由文本）+ 七张卡的 `conclusion` 拼装

甚至连 DeepTutor 论文没做的**冲突处理**，我们在 issue #11 里已经定了规则：「具体记录压过粗
粒度估计——等级是 B1，但这个 C1 词用户已标为『已掌握』，就不要再按 B1 解释它」。

也已经踩过 DeepTutor 明确写下的那条坑：`mastery_reason` 是 `mastery_events` 最新一行的
**反规范化副本**，理由是 `mastery_events` 设备本地，而「读者在第二台设备上看到『熟悉／自动
判定』却没有理由」等于被静默改了学习状态。时间线可以在新设备重来，那句解释不可以消失。

### 学什么

**1（最重要）：把已有的金字塔变成一个能看见的东西。**
我们有全部三层的数据，但它们散在生词详情页、画像页、等级提示条里，没有任何一处让读者
（或我们自己）看到「这个结论是怎么来的」的完整链路。DeepTutor 的 Memory Graph 证明这个
界面本身就是产品价值，不只是调试工具。对 Lantern 的对应物不该是一张力导向图（数据量级
差太多，会很空），而更接近**「学习档案」页：一条时间线 + 每条结论可展开到它的证据行**。
`mastery_events.detail` 里那些数字（distinct_days、exposures、lookups）今天只被渲染成一句
话，其实够画一条完整的下钻路径。

**2：单向引用链值得升级为硬约束。**
今天 `profile_cards.evidence` 是自由文本，靠约定「不进 prompt」。DeepTutor 的做法是让引用
关系是结构性的。Lantern 可做的最小版本：`evidence` 存成结构化引用（表名 + 行 id 列表）
而不是散文，这样「下钻」是查询而不是阅读理解，同时天然堵死「证据被写进 prompt」这条路。

**3：整理作业要有预算旋钮，并且要暴露给用户。**
DeepTutor 的 Settings → Memory 能调更新预算、审计频率、去重。Lantern 的自动分析已经有
「自动分析控制台」这个位置了——把画像重算也纳进同一个预算视图，而不是让它成为另一条
用户看不见的花钱路径。

**4：issue #11 的定位应该抬高。**
按 DeepTutor 的框架看，我们的处境是：L1/L2 层数据完整，**但 L3 组装时漏掉了生词这一整个
面**。外部 MCP 客户端能读到完整生词本，应用内 AI 读不到——不是「少个功能」，是记忆金字塔
缺了一条边。#11 里「先做查词卡注入这个词自己的历史」的收窄是对的，这里只是补一句：那一刀
的本质是**给 L3 接上 vocab 这个 surface**，后续的整章注入是同一条边的加宽。

### 不学什么

- **不学「记忆存 markdown 文件」。** DeepTutor 是服务端形态，文件即接口，用户可以直接编辑。
  Lantern 是 SQLite + iCloud 事件同步，`.md` 文件会立刻在同步、冲突合并、LWW 上制造麻烦。
  可审计性靠**界面**给，不靠存储格式给。
- **不学七面全覆盖。** DeepTutor 有 chat/notebook/quiz/kb/book/tutorbot/cowriter 七个面。
  Lantern 的面实际上只有三个：阅读（含查词）、复习、对话。为不存在的面预留结构就是过度设计。
- **不学 memory agent 常驻。** 三个并行 agent 主动查 trace 更新画像，对本地优先、按次计费
  的 Lantern 是持续的后台成本。我们的 `mastery/mod.rs` 是纯规则打分 + `local_calibration`
  校准几个常数，这个「算法不改、只把写死的数字换成从用户数据量出来的数字」的路线更省、
  更可解释，不要换成 agent 循环。

## 二、多引擎 RAG 的取舍

### 它怎么做

一个知识库选一个引擎，可选七种：

| 引擎 | 适用 | 特点 |
|---|---|---|
| LlamaIndex | 默认、本地 | 本地向量 + BM25 混合检索 |
| PageIndex | 需页级引用、托管 | 推理式检索带来源归属 |
| GraphRAG | 知识图谱推理 | 实体/关系遍历 |
| LightRAG | 快速轻量图检索 | 简化图索引 |
| LightRAG Server | 检索外包 | 外部 HTTP 实例 |
| 腾讯 IMA | 企业环境 | 库留在 IMA 平台 |
| Obsidian Vault | 原地访问 | 直接读写用户的 vault |

论文层面的检索是**双索引融合**：知识图谱 𝒢 抓显式关系 + 稠密向量 ℬ 抓语义相似，两路候选用
**RRF（reciprocal rank fusion，倒数排名融合）**合并、去重、截到上下文预算。

工程上两个细节比引擎列表更值钱：

- **重建索引写到新的版本化目录**，旧版本保留——「重建过程中不摧毁现有索引」。
- **能单独移除失败的文档**，不必删整个库。
- 解析器也可换：纯文本 / MinerU / Docling / markitdown / PyMuPDF4LLM，本地模型下载默认关闭。

### Lantern 现状

我们是**单引擎**，而且是刻意的单引擎：`book_chunks` + `book_chunks_fts`（FTS5）+
`book_chunk_embeddings`，全部设备本地派生数据、不进同步（能从书本身重建）。
`050_contextual_retrieval` 加了 contextual retrieval——给每个 chunk 生成一行「身份句」，
并让 `book_chunk_embeddings.context_sha256` 参与失效判断。这一路我们做过 A/B 实盘验证
（`contextual-retrieval-ab-{jane-eyre,moby-dick,pnp}.md`）。

### 学什么

**1：索引重建的版本化与部分失败恢复。**
这是最直接可搬的一条，而且跟引擎选择无关。今天 `book_index_state` 有 `status` 和 `error`，
但重建是原地的——一本大书重建到一半失败，中间态是什么？DeepTutor 的答案（新目录写入、
旧的保留、单文档可移除）是成熟做法。对我们就是：重建写新 `index_version`，切换是最后一步，
以及允许「这一章解析失败，其余仍可检索」而不是整本 `status = 'error'`。

**2：RRF 值得试，成本很低。**
我们有 FTS5 和向量两路，融合方式目前是自己的排序逻辑。RRF 是一行公式、无参数、无需训练，
是混合检索的默认答案。可以在现成的 A/B 框架里加一组对比，不需要新基建。

**3：解析器可插拔的思路，对 PDF/OCR 那条线有用。**
我们已经有 OCR 分支（`commands/ocr/`、`scanned-pdf-ocr-*` 系列文档）。DeepTutor 把「用哪个
解析器」做成用户可见设置、并默认关闭本地模型下载，是个好的默认——重解析器是可选增强，
不是装机即下载。

### 不学什么

- **不学多引擎可选。** 七个引擎对一个通用工作台是必要的（用户带着各种形态的资料来）；
  Lantern 的语料是**一本书**，结构已知、体量已知、来源可信。多一个引擎就是多一套索引状态机、
  多一份失效逻辑、多一类只有少数用户会碰的 bug。单引擎 + 把 contextual retrieval 做透是对的。
- **不学 GraphRAG/知识图谱。** 小说和非虚构章节的检索瓶颈不在实体关系上（我们的
  `person_aliases` + `person_alias_embeddings` 已经是这个需求的定点解法，比通用 KG 便宜得多）。
- **不学托管/外部检索服务。** PageIndex、LightRAG Server、腾讯 IMA 都意味着书的正文出本机。
  Lantern 的本地优先是产品主张，不是实现细节。

## 三、Book / living book 交互形态

### 它怎么做

Book 把选定的资料（知识库 / 笔记本 / 题库 / 聊天记录）编译成「活书」——不是静态 PDF，
是由**带类型的块（typed blocks）**构成的阅读环境。四个阶段：

1. **输入快照与提案** — 冻结用户意图、聊天历史、笔记、知识库、题目类别；提出范围、受众、
   目标、结构。
2. **课程主干与概念图** — 先对选中材料做定向扫描，再由 spine synthesizer 构造章节结构和
   概念图，**显式写出先修关系和主题覆盖**。
3. **块级页面编译** — 每一页是**有序的类型化块序列**，不是一整篇文档。块类型包括：文本讲解、
   提示框、测验、图、交互演示、动画、代码、时间线、闪卡、深入链接、小节总结、概念图块。
4. **持续交互与补救** — 单块可重生成/插入；从一个概念可以派生「深入子页」；**每一页有自己
   的页级对话**；测验结果更新进度记录。

两个机制性细节：

- **结构先审后生成。** 系统先提章节大纲给用户批准，再生成内容——「你审的是结构，而不是被动
  接受一次性盲出的结果」。
- **页面对源做指纹。** `deeptutor book health` / `book refresh-fingerprints` 能检测编译页与
  源知识库的**漂移**，标出需要刷新的页。

论文明确标注：Book Engine 是**架构示例**，对留存、参与度、打断成本、真实学习效果的影响
**需要纵向人类研究**，目前没有量化评估。

### Lantern 现状

我们没有「生成一本书」这回事，而且不该有——**Lantern 的书是用户自己的书**，这是产品的根。
但块级、页级的那套结构，跟我们几个已有/在建的东西是同构的：

- `explanations`（048）——段落级解释，已经有缓存/用户数据二分（`saved`）和 **prompt 指纹**
  （`variant` = explanation_mode + cefr_level），「读者把 CEFR 从 B1 调到 C1 之后，回放一条
  B1 的解释是 bug，不是省钱」。这就是 DeepTutor 的**漂移检测**，我们已经有了，只是维度是
  prompt 参数而不是源文档。
- `book_summaries`（023）、章末回顾（`chapter-end-recap-mockup.html`）——生成的、附着在书上的
  结构化内容。
- `review_piles` / `vocab_watchlist` / 闪卡复习——DeepTutor 块类型里的 flashcard、quiz。

### 学什么

**1：把「AI 生成内容」统一成带类型的块 + 单块可重生成。**
今天章末回顾、书籍摘要、段落解释各自是一坨文本，重来只能整体重来。DeepTutor 的块模型给出的
收益很实在：**用户对一段不满意，只重生成那一段**，成本和打断都小一个量级。这对按次计费的
Lantern 尤其值——重生成一整章回顾是真金白银。

**2：漂移指纹应该扩展到源侧。**
`explanations.variant` 已经覆盖了「prompt 参数变了」。缺的是「**源变了**」：换了同一本书的
另一个版本、重新解析、OCR 重跑之后，旧解释还挂在那儿。加一个源指纹（我们已经到处在用
`source_sha256`）就能标记「这条解释来自旧版本正文」。

**3：结构先审后生成，是省钱也是尊重。**
任何「一次生成一大坨」的功能（书籍摘要、章末回顾、复习清单），先给结构、再生成内容，比
直接出成品好：用户能在便宜的阶段拦下方向错误。

**4：页级对话这个位置。**
DeepTutor 每页有自己的对话上下文。Lantern 的书内对话目前是**整本书一个会话**。章节级/段落级
的对话入口是否值得，是个产品问题（不是我该定的），但结构上我们已经有 `chapter`
这个到处在用的自由文本标签可以挂。

### 不学什么

- **不学生成整本书。** 用户导入自己的书是 Lantern 的前提。「让 AI 给你编一本书」是另一个产品。
- **不学概念图/先修关系图。** 对课程化学习有意义，对读一本小说没有。我们的 `person_aliases`
  是这个方向上唯一被验证有需求的切面。
- **不学 Partners / IM companion（主动找你聊的 AI 伙伴）。** 与 Lantern 已确立的
  「复习文案不施压」原则直接冲突：不催促、不指责、不倒计时、不报欠账天数。一个会主动敲你的
  伙伴，本质上就是催促。

## 四、总结：三条最值得动的

按「价值 / 成本」排序，独立于上面的分节：

1. **给 L3 接上 vocab 这个面**（issue #11 的第一刀）。数据全在，缺的只是一段 prompt 前缀。
   最小的改动，消掉最刺眼的落差。
2. **学习档案页：结论 → 证据的下钻**。我们有别人没有的东西（完整的、设备本地的、
   带 `detail` JSON 的证据链），却没有一个地方展示它。这既是产品差异化，也是我们自己
   调试打分规则的工具。
3. **索引重建版本化 + 部分失败恢复**。纯工程，无产品决策，把一类「重建到一半炸了」的
   故障模式整个消掉。

明确**不做**的三条，记下来免得以后反复讨论：多引擎 RAG、知识图谱、主动打扰的 AI 伙伴。
